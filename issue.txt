Claude Code “cb is not a function” Tool Error – Analysis and Solutions

Issue Overview

When using Claude Code connected to an Azure Cognitive Search MCP server (Model Context Protocol server), attempts to invoke the server’s tools can fail with an error message: “cb is not a function.” In practice, this means Claude Code tried to call a tool’s handler or callback (cb) but the call could not be completed. This error typically arises when there is a mismatch in how the tool is registered or invoked. The underlying MCP integration expects certain structures and callbacks; if those aren’t met, the tool call fails.

Understanding the Error and Root Causes

Several root causes can lead to the “cb is not a function” error in this context. Below are the primary culprits identified:

•	Incorrect Tool Invocation Format (Missing operation/params): The Azure Search MCP tools are designed so that each tool (e.g. IndexManagement, DocumentOperations) supports multiple operations. Calling these tools requires a JSON payload containing an "operation" name and a "params" object. Initially, users (or the LLM) were invoking tools without following this structure – for example, calling a tool with a raw string or wrong JSON shape. Because the tool descriptions did not clearly instruct Claude to include an "operation" field, Claude would call the tool incorrectly, causing the server to error out. In the Azure Search MCP evaluation, the root cause was identified as the LLM not providing the expected parameter structure, leading to cb is not a function errors[1]. The fix was to update the tool documentation so that Claude always calls tools like: {"operation": "<operationName>", "params": {…}}[2]. In short, an unsupported usage pattern – omitting the required fields – triggered the callback error.

•	Improper Tool Registration (Callback Mismatch): On the server side, the MCP tools must be registered with the MCP SDK using the correct schema. In the Azure Search MCP server code, each dynamic tool uses a Zod schema for its parameters. The MCP SDK expects a raw object shape for the parameters, not a full Zod object. If a developer mistakenly passes a ZodObject directly into server.tool(...) instead of its shape, the SDK can misinterpret the arguments. This mis-registration leads to an internal misalignment where the callback handler (cb) isn’t properly set, hence the runtime error. In fact, a comment in the Azure Search MCP code notes that passing a ZodObject causes the SDK to treat it as annotations, “leading to a runtime ‘cb is not a function’ when invoking the handler”[3]. The resolution was to pass the schema’s shape (schema.shape) rather than the ZodObject itself during tool registration[3]. This API mismatch between the MCP server code and the SDK was a direct cause of the error.

•	Output Schema or Callback Format Issues: Even if the tool is invoked correctly, the tool’s return value must conform to MCP’s expected format. The Model Context Protocol wraps tool outputs into a structured response (often with a structuredContent field for machine-readable data and a content array for text segments). If a tool’s result is not packaged correctly, the MCP agent might fail when trying to process or call the callback with that result. For example, one MCP server’s documentation explains that “cb is not a function” often occurs if the tool’s return does not match the expected format or if the callback usage is incorrect[4]. The expected solution is to ensure the tool returns a plain object matching the schema, e.g. an object with structuredContent (structured data) and content (text) fields[5]. In practice, using a helper like a ResponseFormatter (as done in the Azure Search MCP server) ensures that the tool’s output is wrapped in the proper MCP response shape (including structuredContent) to avoid callback errors. Notably, developers should avoid returning complex class instances or TypeScript interface types directly – return a normal JSON object that matches the declared schema[5].

•	Version or Protocol Mismatch: If using older or mismatched versions of the MCP SDK or Claude Code, there might be known bugs or changes in expected patterns. For instance, earlier iterations of community MCP servers encountered the “cb is not a function” error until they adjusted their code. Ensuring you’re using an up-to-date Model Context Protocol SDK and following the latest protocol spec is important. (For example, the addition of multi-operation tools via an "operation" field is a newer pattern – older tool integrations might not have anticipated this and thus needed updates.) In the Azure Search MCP integration, a number of fixes (such as properly extracting data from responses and including all required fields) were applied to align with the expected API[6]. While the error itself isn’t a Claude bug per se, it can manifest if your tool integration doesn’t precisely meet Claude’s MCP interface expectations.

Diagnosing the Problem

To pinpoint the cause in a given scenario, consider these diagnostic steps:

1.	Inspect Tool Descriptions and Calls: Check how Claude Code attempted to call the tool. If possible, use Claude’s MCP Inspector or logs to see the exact JSON it sent. If the call lacks an "operation" or "params" field (or these are mis-specified), that’s a red flag. The error can occur client-side if Claude didn’t structure the call correctly. In that case, improving the tool’s description with explicit usage instructions can guide the model. (The Azure MCP server maintainers added a “USAGE: …” prefix in each tool description with an example call format[7], which helped the model avoid the error.)

2.	Enable Server-Side Logging: On the MCP server, enable verbose logging or run it in a debug mode. The error cb is not a function might come with a stack trace in the server console. This can reveal if the error originates during tool registration (likely a coding issue) or at invocation time when formatting the response. If the stack points to the MCP SDK internals right when a tool is called, it suggests a registration/schema issue (like the Zod object problem). If it fails while constructing the response, it could be an output formatting issue.

3.	Test Tool Handlers in Isolation: Use a direct method to call the tool outside of Claude (for example, via a small test script or the provided createToolWrapper utility if available). By invoking the tool function with a known good input, you can see if it returns a well-formed result or throws an error. The Azure Search MCP project, for instance, provides a direct invocation wrapper for tools to facilitate testing[8]. If calling the tool directly works and returns structured data, the issue might lie in how Claude is calling it (format issue). If it throws or returns something unexpected, the issue is in the tool implementation.

4.	Validate the Schema and Return Structure: Cross-check the tool’s declared schema vs. what it actually returns. If the tool declares that it returns, say, an object with certain fields, ensure all those fields are present. Also verify that you registered the tool with the correct parameter schema. A quick sanity check is to ensure you used the .shape of Zod schemas (if using Zod) when registering with server.tool(), as passing a full ZodObject can break the callback handler[3]. Similarly, verify that the response object includes content and any required metadata (structuredContent was added by the Azure tools so that Claude receives a structured JSON alongside the textual content[5]).

5.	Search for Known Issues: It can be helpful to see if others have encountered the exact error in similar contexts. The “cb is not a function” message is not unique to Azure Search – it has appeared in other MCP integrations. For example, an Adobe Express MCP server guide explicitly notes this error and attributes it to incorrect callback usage or output schema mismatches[4]. Knowing this can save time by focusing your troubleshooting on callback formats and schema compliance. If using an open-source MCP server template, check its repository or issue tracker for mentions of this error (in one case, a Tabby MCP server had an open bug for a specific tool function yielding this error, indicating a likely implementation bug).

Solutions and Workarounds

Depending on the root cause, the remedies for the “cb is not a function” issue are:

•	Clarify and Enforce the Tool Call Format: Ensure Claude (the LLM) is given clear instructions on how to call the tool. Update the MCP server’s instructions and tool descriptions to list the available operations and the exact JSON structure required[2][9]. In practice, after the Azure Search MCP team added explicit examples (e.g. usage of {"operation": "list", "params": {...}}), Claude began calling the tools correctly and the error disappeared[10][11]. As a user, always include the "operation" field (and use an empty {} for params if none are needed) when prompting Claude to use one of these tools[11]. This aligns the LLM’s requests with the server’s expectations.

•	Fix Tool Registration Code: If you maintain the MCP server code, adjust how tools are registered with the Model Context Protocol SDK. Make sure you’re passing a plain object schema for parameters rather than complex schema objects. For example, extract the shape from validation schemas (as done in the Azure Search server code) so that the MCP framework correctly recognizes the parameters schema[3]. This change ensures the internal callback (cb) is set up properly by the SDK. Additionally, register any necessary annotations or metadata as separate arguments rather than mixing them with the schema. By aligning with the SDK’s expected function signature, you prevent it from misinterpreting your inputs (which was the cause of the callback not being a function).

•	Return a Proper MCP Response Structure: In your tool handler implementation, always output data in the format the MCP client expects. Typically, this means returning a JSON object with a structuredContent field (containing the raw result data) and a content field (an array of text blocks or messages for the model)[5]. If you use helper classes or interfaces, convert them to plain objects before returning. The Azure Search tools leverage a ResponseFormatter to automatically wrap the result into an MCPResponse with both content and structuredContent, which is a best practice. If you’re not using such a utility, manually ensure all required fields in the protocol’s response schema are present (missing expected fields in structuredContent can also trigger the error[12]). By returning the full expected structure, the MCP client’s callback logic will find everything it needs and not throw an error.

•	Upgrade or Match Versions: If you suspect a version mismatch, update to the latest version of Claude Code and the MCP SDK. This can resolve any underlying incompatibilities. For instance, as MCP and Claude evolved, the conventions (like multi-operation tools and elicitation capabilities) have been refined. Using a known-good combination (and referencing official documentation or updated templates) reduces the chance of hitting unknown bugs. In the Azure Search integration case, all tools were ultimately marked “✅ Working” after applying the above fixes[13], indicating compatibility with the current Claude Code environment. Ensure you also refer to Anthropic’s official MCP integration guide and adjust any deprecated patterns. (For example, if an older guide suggested a different return format, follow the latest guidance as shown above.)

Conclusion

The “cb is not a function” error is essentially a symptom of integration issues between Claude Code and the MCP server tools – not a random failure of Claude itself. It usually means the tool invocation or response didn’t adhere to the expected interface, causing the underlying callback mechanism to break. By addressing the root causes – clarifying the tool usage format for the LLM, correcting any tool registration mistakes, and ensuring output schema compliance – you can eliminate this error. In fact, after the Azure Search MCP team implemented these fixes, they confirmed that “All Azure Search MCP tools are fully functional and ready for use with Claude Code,” with proper invocation no longer causing errors[14].
